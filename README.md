# Contract Review Agent

**Local-first, auditable LLM-assisted supplier contract review.** This prototype evaluates a UTF-8 plain-text contract against six predefined company policies and returns one finding per rule: `COMPLIANT`, `NON_COMPLIANT`, or `NOT_FOUND`, with supporting quotations and a separate `requires_human_review` flag.

**This is decision support, not legal advice or autonomous contract approval.** A human reviewer remains responsible for final approval.

## Architecture and decisions

```text
UTF-8 contract + six predefined policies
                  |
                  v
      Local LLM via vLLM
      Structured candidate/fact extraction (V2)
                  |
                  v
      Exact evidence verification
                  |
                  v
      Six deterministic Python policy evaluators
                  |
                  v
      Six findings + human-review flags
                  |
                  v
      CLI JSON output + JSONL audit events
```

- **V0 — Direct LLM classification:** One structured model call produces the six policy findings. Useful as a baseline, but exposed numerical reasoning, clause aggregation, and evidence errors.
- **V1 — Evidence verification:** Adds deterministic exact-quotation checking and flags invalid evidence for human review. A genuine quote can still support an incorrect interpretation.
- **V2 (default) — Structured extraction + deterministic evaluation:** The LLM extracts candidate clauses and typed facts; Python checks quotations, evaluates the policies, aggregates multiple candidates, and generates one finding per rule. Final V2 statuses are not directly generated by the LLM.

The six rules cover termination-for-convenience notice (at least 30 days), supplier invoice payment (within 60 days), liability capped at total contract fees, Turkish governing law including incorporated schedules, mutual confidentiality, and no automatic renewal. The exact rule definitions and exceptions live in `config/rules.json` and the evaluators.

**Why local inference?** Supplier contracts can contain confidential commercial terms and personal data. The prototype was developed with Qwen3-8B-FP8 served through vLLM, motivated in part by enterprise AI experience at Akbank Technology and the importance of controlling data flows in sensitive environments. Self-hosting avoids requiring an external model provider for inference, but **does not by itself guarantee privacy, regulatory compliance, or security**. Production deployment would need network isolation, access control, encryption, and log-retention controls.

## Installation

### 1. Prerequisites

- Linux or WSL with **Python 3.11+**, `venv`, and `pip`.
- A running **vLLM-compatible inference server** with an OpenAI-compatible chat-completions endpoint supporting the `structured_outputs.json` schema constraint used by this project. The recorded runs used **Qwen3-8B-FP8**.
- Hardware and a model supported by your chosen vLLM installation. No Docker setup is required by this repository.

The application is configurable rather than tied to the original model path or workstation; **compatibility and accuracy with other models are not guaranteed**.

### 2. Clone and install the CLI

```bash
git clone https://github.com/melihdilbaz/contract-review-agent.git
cd contract-review-agent
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
```

### 3. Start your model server

Install vLLM and obtain a compatible model using the **official vLLM installation instructions** appropriate for your GPU/environment. The following is an illustrative startup command, **not a model download or vLLM installation command**:

```bash
vllm serve /path/to/your/model \
  --served-model-name contract-review-qwen3-8b \
  --host 127.0.0.1 \
  --port 8000
```

Run the inference server in a **separate terminal** and leave it running. Replace `/path/to/your/model` with a real model directory or supported model identifier. `contract-review-qwen3-8b` here is only an example served-model ID, not a guaranteed available model.

### 4. Configure environment variables

In the terminal where you will run the CLI:

```bash
cp .env.example .env
```

Edit `.env` to match your server, for example:

```dotenv
LLM_BASE_URL=http://127.0.0.1:8000/v1
LLM_MODEL=contract-review-qwen3-8b
LLM_API_KEY=unused
```

Then load those variables into your shell:

```bash
set -a
source .env
set +a
```

**Important:** The app does **not** automatically load `.env`. `LLM_MODEL` must equal the name exposed by your server, and `LLM_BASE_URL` should include `/v1` for a standard vLLM OpenAI-compatible endpoint. `LLM_API_KEY` is optional for an unauthenticated local server; never commit a real API key.

Check server accessibility:

```bash
curl --fail --show-error "$LLM_BASE_URL/models"
```

If you use a different backend, confirm that it supports the **vLLM-specific `structured_outputs` JSON-schema request field**, not merely a generic OpenAI-compatible endpoint.

## Run a contract review

From the repository root, with the server running and environment variables loaded:

```bash
# Default pipeline: V2
contract-review review --contract data/contracts/contract_a.txt
```

The CLI prints JSON with the version, contract path, six policy findings, and execution metadata. It also writes audit events to `logs/reviews.jsonl`.

To run the earlier versions:

```bash
contract-review review --version v0 --contract data/contracts/contract_a.txt
contract-review review --version v1 --contract data/contracts/contract_a.txt
```

To review your own agreement, provide a path to a **UTF-8 `.txt` file**:

```bash
contract-review review --contract /path/to/your_contract.txt
```

PDF/DOCX ingestion, contract edits, and autonomous approval are **not implemented**. Use the command from the repository root so the bundled relative paths and evaluation assets resolve as expected.

## Evaluation: how to reproduce the results

The fixed benchmark contains **3 synthetic contracts × 6 policies = 18 rule-level expected outcomes**, including **7 violations**. Canonical inputs are `data/contracts/`, `data/ground_truth.json`, and `config/rules.json`.

### Read the saved results — no model required

```bash
contract-review eval --version all
```

This is **report mode** (the default); it reads the committed evaluation JSON files. It does **not** rerun inference. Individual versions can also be inspected with `--version v0`, `v1`, or `v2`.

### Run new live evaluations — model required

```bash
# Re-evaluate one version with your configured inference server
contract-review eval --version v2 --mode live
```

You can also select `v0` or `v1`. `--version all --mode live` is **not supported**. Live runs write `eval/results/<version>.json` and may replace the saved result for that version in your local checkout; preserve or copy the existing result first if you need to retain it. The frozen initial V2 baseline is separately stored in `eval/baselines/v2_initial.json`.

### Run the test suite — no model required

```bash
python -m pip install pytest
python -m pytest tests/ -q
```

**Recorded local test result:** 35 passed. The tests do not establish that arbitrary third-party LLM endpoints are supported.

### Recorded performance

The table reports **separate live inference runs** on the same frozen dataset, **not** a controlled paired comparison of V0/V1/V2.

| Metric | V0 | V1 | V2 initial |
| --- | ---: | ---: | ---: |
| Classification accuracy | 66.7% | 55.6% | **77.8%** |
| Violation recall | 57.1% | **71.4%** | **71.4%** |
| Exact evidence validity | 50.0% | 33.3% | **100.0%** |
| Human-review recall | 0.0% | **100.0%** | 50.0% |
| Successful contract coverage | 66.7% | 100.0% | 100.0% |
| End-to-end correctness | 22.2% | 22.2% | **72.2%** |
| Candidate recall | — | — | **84.0%** |

V2 initial: **14/18** correct classifications, **5/7** violations detected, **13/18** end-to-end correct results, and **21/25** relevant clause references extracted. All **21/21** extracted candidate quotations passed exact-text verification.

### What the metrics actually tell us

- **Classification accuracy (correct policy statuses / 18):** V0 reached **12/18 (66.7%)**, V1 **10/18 (55.6%)**, and V2 initial **14/18 (77.8%)**. V2 produced four more correct statuses than V0 in these recorded runs, but this does **not** isolate the benefit of Python evaluators: the LLM task, extraction schema, and live responses also changed.
- **Violation recall (detected violations / 7):** V0 detected **4/7 (57.1%)**; V1 and V2 detected **5/7 (71.4%)** each. V2's stronger overall accuracy did **not** improve violation detection beyond V1. Missing a prohibited clause remains consequential even when most other statuses are correct.
- **Exact evidence validity (verbatim quotations / returned quotations):** V0 **50.0%**, V1 **33.3%**, V2 **100.0%**. This measures whether *generated quotations* appear in the source, not whether verification code caught invalid ones, whether the quoted provision applies, or whether the extracted interpretation is correct. V1's lower rate reflects the independently generated model output; it is not evidence that the checker made grounding worse.
- **Human-review recall:** V0 **0.0%**, V1 **100.0%**, V2 **50.0%** against the benchmark's review-required cases. V1's escalation was more sensitive in its recorded run; V2 still missed cases requiring human attention. High classification accuracy should not be conflated with safe escalation behavior.
- **End-to-end correctness:** V0 **4/18 (22.2%)**, V1 **4/18 (22.2%)**, V2 **13/18 (72.2%)** under the benchmark's combined decision/evidence/review checks. This is the clearest observed improvement in the complete workflow, but it remains a small-sample result.
- **Candidate recall (V2 only):** **21/25 (84.0%)** expected relevant clause references were extracted. This is an *upstream ceiling*: a policy evaluator cannot assess a clause it never receives, even if its rule logic is perfect.
- **Successful contract coverage:** V0 **66.7%**, V1 and V2 **100.0%** in the recorded runs. This reports completion of the reviewed contracts, not decision accuracy.

**Controlled comparison vs. separate runs.** A separate **V0/V1 paired replay** (`eval/results/paired_v0_v1.json`) reuses frozen model responses to isolate the effect of the verification layer. In that replay, both versions had **66.7% classification accuracy** and **50.0% exact evidence validity**; the value of V1 is its explicit invalid-evidence detection/escalation rather than a demonstrated improvement in the raw quotations. The table above instead contains **independent live runs**. V2 is **not paired** against V0/V1 because it asks the model to extract candidates rather than issue final classifications.

**What these numbers do not establish.** The benchmark has only **three synthetic contracts, 18 policy outcomes and seven violations**; one changed outcome materially shifts a percentage. No confidence intervals, real-world legal accuracy, cross-model reproducibility, latency benchmark or inference-cost comparison are claimed. The table is the **frozen V2 initial baseline**, before a targeted R05 evaluator correction; the full 18-outcome run has **not** been repeated after that change. Accordingly, the recorded V2 metrics are **not** a fresh measurement of the latest evaluator code.

## Failure analysis: current architectural limits

The **five incorrect V2 initial outcomes** are informative because they occur at different stages:

| Failure | Where it arose | Why the current design did not prevent it |
| --- | --- | --- |
| **A/R03, B/R03 — liability** | **Extraction completeness** | The LLM omitted fee information needed for the cap comparison. Deterministic arithmetic cannot recover an absent operand. |
| **B/R05 — confidentiality** | **Evaluator applicability** | Python incorrectly filtered a relevant general confidentiality exclusion. Deterministic code is testable, not automatically correct. A targeted fix was made after the frozen baseline. |
| **C/R01 — termination** | **Candidate coverage** | A relevant termination provision was not extracted. Whole-document input does not guarantee that every important clause is surfaced. |
| **C/R06 — renewal** | **Semantic fact accuracy** | Language about continued performance was interpreted as an explicit no-auto-renewal fact. The quotation could be textually valid while the extracted claim was wrong. |

**Remaining gaps:** `NOT_FOUND` cannot always distinguish a genuinely absent provision from a missed extraction; exact substring checks do not verify meaning or applicability; exceptions, schedules and clause precedence remain difficult; human-review recall is incomplete; and whole-document processing has not been validated on long contracts. Audit logging improves traceability but may retain sensitive contract text and is not a substitute for enterprise controls.

## Why V3 was not implemented — and what comes next

**Deliberate stopping point:** The case-study goal was a small, measurable contract-review pipeline, not a production legal platform. V0 established a baseline; V1 tested deterministic grounding checks; V2 tested separating semantic extraction from rule evaluation. Adding retrieval, more agents or a product UI before characterizing those failures would introduce more variables, infrastructure and debugging work without evidence of better outcomes. The limited synthetic benchmark also cannot justify production-readiness claims. **V3 was not built or evaluated.**

With more time, the next changes would follow the observed failure modes, in priority order:

1. **Extraction completeness and semantic fact verification (first):** Define mandatory facts per policy (for example, fee totals before liability comparison); flag missing or inconsistent fields for human review. Check that a quoted clause actually entails the extracted fact, not merely that the quote exists. Target **A/R03, B/R03, C/R01 and C/R06**. Evaluate candidate recall, fact-level precision/recall and downstream violations—not just quote validity.
2. **Applicability, exceptions and precedence:** Model general vs. narrow exclusions, incorporated schedules and contradictory terms; add focused regression cases before changing evaluator logic. Target **B/R05** and similar clause-filtering errors.
3. **Clause-aware retrieval for long agreements:** Only when document size warrants it, segment by sections and preserve clause IDs, schedule links and cross-references. Compare against whole-document extraction on the same long-contract set, including *retrieval recall*, rather than assuming RAG improves accuracy.
4. **Stronger safety and evaluation:** Expand to more diverse synthetic and permissioned real-world drafting patterns, numeric edge cases and prompt-injection attempts; evaluate false-compliance rate, human-review precision/recall and regression stability across repeated runs. Keep approval human-controlled.
5. **Enterprise readiness and reviewer feedback:** Add authenticated access, RBAC, log redaction/retention, encryption and offline deployment checks. Record reviewer corrections as new frozen regression cases, not as automatic contract approvals.

These are **proposed extensions**, not existing capabilities or measured V3 results. The next milestone should be an improved evaluation set and evidence that the highest-priority fixes reduce the observed errors before expanding the architecture.

## Security, privacy, and auditability

Contract text is **untrusted input**, not instructions for the agent. Schema validation, exact quotation checks, deterministic evaluation, and human oversight provide safeguards but do **not** fully prevent prompt injection or incorrect legal interpretations.

Audit events are appended to `logs/reviews.jsonl` and can include prompts, raw model outputs, token usage, findings, failures, and correlation metadata. **The log may contain sensitive contract text.** Logs and `.env` are excluded from version control. In production, enforce access control, encryption, restricted network exposure, retention/deletion policies, and appropriate handling of personal data.

**Privacy note:** Running an LLM locally means inference requests can stay inside your controlled environment; it is not a formal security or regulatory compliance certification. Review data-processing requirements before using real agreements.
